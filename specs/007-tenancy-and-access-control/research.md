# Research — Feature 007 Tenancy and access control

Verification date: 2026-08-04. Shared package research is in `docs/replatform/technical-research.md`; global-role/team behavior was verified against [Spatie Permission v8 Teams permissions](https://spatie.be/docs/laravel-permission/v8/basic-usage/teams-permissions) and the locked 8.3.0 source.

| ID | Decision | Reason | Rejected |
|---|---|---|---|
| RES-007-001 | One database with explicit tenant ownership | Approved product boundary and minimum shared-hosting complexity. | separate DBs/subdomains/tenancy package |
| RES-007-002 | Spatie Permission 8.3 teams keyed by tenant ID | Current Laravel 13-compatible configurable RBAC. | custom ACL or fixed roles |
| RES-007-003 | Code-owned permission catalogue with React/TailAdmin role UI | Keeps the stable allowlist in application code and uses the branch's native TailAdmin page patterns without a second UI stack. | Shield/Filament role UI; application-owned generic role builder |
| RES-007-004 | Request-scoped TenantContext + explicit query predicates | Fail-closed and testable; permission team context alone does not scope business data. | hidden global scope as sole isolation |
| RES-007-005 | Protected global Administrator role | Product requires platform control but no invariant bypass. | super-admin `Gate::before` allowing everything |
| RES-007-006 | Tenant user belongs to one tenant | Approved model; avoids membership pivot/switch complexity. | multi-tenant memberships |
| RES-007-007 | No impersonation | Real actor+tenant audit and simpler security. | login-as tenant user |
| RES-007-008 | Native TailAdmin React resources/onboarding pages | Existing branch components are sufficient and keep one application frontend. | Filament/Livewire resources; mandatory onboarding state machine |
| RES-007-009 | Two explicit Tenant operational setting columns and typed DTO/Actions | Only two approved settings exist; explicit schema, authorization and audit are simpler and safer than an open-ended settings engine. | generic key/value tenant settings or consumer-owned Tenant queries |
| RES-007-010 | Separate protected Administrator abilities for quota and deletion-reason management | Both settings affect one tenant but remain platform-administered; separate identifiers preserve least privilege and explicit audit while tenant roles receive neither. | tenant-role setting control or one undifferentiated settings authority |
| RES-007-011 | Tenant stores nullable restrictive `created_by_user_id` and only the latest `state_changed_by_user_id`/`state_changed_at`; full lifecycle history is append-only audit | Satisfies the normative actor/timestamp evidence with three nullable forward-safe fields while avoiding duplicated deactivate/reactivate columns and retaining complete history in its authoritative audit stream. | one actor/timestamp pair per transition; cascade/null-on-delete actor FKs; audit-only current-state attribution |
| RES-007-012 | Global Administrator role assignments use reserved package team key `0`, which is never a Tenant, behind the Feature 001 `PlatformAdministrator` boundary; the role holds the complete stable catalogue | Spatie Permission 8.3 requires the relationship pivot team key while global roles themselves retain nullable `tenant_id`; the complete catalogue supplies the actor's approved selected-tenant abilities, while the boundary preserves tenantless identity, prevents permission-team leakage and leaves Policies/ownership/invariants mandatory. | fake Tenant `0`; per-tenant Administrator memberships; protected-only Administrator unable to operate in selected tenants; global `Gate::before` bypass; nullable unsupported package pivot |
| RES-007-013 | Administrator selection uses session key `tenant_context.tenant_id`; middleware passes one immutable context through the request attribute keyed by `TenantContext::class`; missing/inactive failures use the stable `AuthorizationException` messages; enter/leave audit precedes session mutation | Keeps T007-003 independently testable without taking T001-007 bootstrap/provider ownership, lets the later scoped binding consume the same request value, preserves Laravel's 403 rendering with the stable code, and ensures failed audit cannot change selected context. Tenant users ignore the selection key and always derive their fixed membership. | container singleton/context globals; new exception hierarchy; route/session input authorizing tenant users; session mutation before audit; random hidden correlation ID |
| RES-007-014 | The foundation-only `ResolvesTenantOwnedBindings` declaration carries one explained inline `trait.unused` PHPStan suppression until the first concrete tenant-owned model consumes it | T007-004 must deliver the shared route-binding boundary before Feature 002 creates the first eligible production model. PHPStan otherwise rejects the required, intentionally pre-consumer trait. The local identifier-only annotation follows the installed Filament convention; once a real model uses the trait, unmatched-ignore reporting makes the annotation fail and forces removal. | global PHPStan exclusion; disabled unused-trait analysis; fake production consumer; premature generic base model; accepting a failing static gate |
| RES-007-015 | `AuthorizesTenantOwnership` receives actor, ability, nullable context, resource, the permission registrar and protected Administrator boundary explicitly; a tenant actor's current Spatie team must equal the persisted actor/context tenant before its exact ability can allow, while Administrator checks remain inside the scope-0 boundary with prior-team restoration. It then checks actor/context identity, fixed membership, a genuinely persisted selected Tenant and persisted same-tenant resource ownership. Each owning Policy checks its resource current-state/domain invariants afterward, and tenant Active/Inactive remains the request middleware boundary. `AuthServiceProvider` is explicitly listed in `bootstrap/providers.php` and registers no application `Gate::before`. | Preserves the normative authorization order without making T007-012 depend on T001-007's container binding, closes cross-team ability reuse, avoids recursive/global Gate bypass, rejects force-filled context identities, returns the same safe not-found result for missing or foreign resources, and keeps feature-specific state rules with their owning Policies. Laravel 13.22 loads application providers from `bootstrap/providers.php`, so provider creation alone is inert. | trusting the registrar's unrelated current team; changing team silently inside a Policy; hidden `app(TenantContext::class)` lookup; generic state interface; duplicate tenant-active rule; role-name branch; direct catalogue ability Gate recursion; unregistered provider; Administrator `Gate::before` |
| RES-007-016 | Reinforced tenant deactivation requires an explicit server-validated token equal to the target tenant's exact code; the React/TailAdmin confirmation dialog presents a required text input and passes that value to the domain Action | Q-024 fixes which operations require reinforced confirmation but leaves the mechanism technical. Matching the stable target code is deterministic, target-bound and requires no speculative session/token service; empty, case-changed or other-tenant values fail with `DESTRUCTIVE_CONFIRMATION_REQUIRED`. | any non-empty string; client-only dialog boolean; password re-entry infrastructure; random/session token service; hard-coded generic phrase |
| RES-007-017 | Tenant lifecycle writes use audit event types `tenant.created`, `tenant.updated`, `tenant.deactivated` and `tenant.reactivated`; every Action reloads the persisted active tenantless actor before mutation/attribution, lifecycle timestamps are generated explicitly in UTC, and the foundational create/update fields accept nonblank names/codes, three ASCII-letter currency codes, ASCII-letter language identifiers up to ten characters, valid PHP timezones and non-negative `DECIMAL(12,6)`-representable VAT strings. Duplicate-code races are converted to a `code` `ValidationException`; current-state/CAS conflicts use the existing `STALE_VERSION` code. The foundational update Action changes only name, code, currency, language, timezone and default VAT | Exact event identities and persisted actor/time evidence make audit tests deterministic under tenant presentation timezone changes. The six fields are the approved Q-012 tenant identity/local-economic inputs; bounded validation matches the actual schema without inventing a business VAT ceiling or external catalogue, and native validation avoids leaking database exceptions. Lifecycle columns belong to lifecycle Actions, branding/contact/logo to T007-020, and attachment quota/deletion-reason settings to T007-022. | stale/force-filled actor attribution; ambient-timezone persistence; raw duplicate/overflow database exception; arbitrary currency/language text; negative/out-of-representation VAT; uncatalogued lifecycle-state code; generic `tenant.changed`; arbitrary mass assignment; lifecycle changes through update; premature branding or operational-setting ownership |
| RES-007-018 | `CreateTenant` requires exactly one global seeded Editor and one Viewer source template, then copies them into two tenant-owned roles with the same names and exact permission sets inside the tenant-creation transaction; missing or duplicate global source rows are an unexpected configuration `LogicException` and roll back without a new user-facing domain code. Later catalogue seeding continues to update only the global source templates and never overwrites tenant copies | Makes the approved templates independently editable per tenant without coupling tenant creation to Shield UI or allowing one tenant's customization to affect another tenant. Failing closed on duplicate nullable-global rows avoids nondeterministic `keyBy` selection; a failed role copy or audit write rolls back the tenant and both copies. | arbitrary first duplicate template; invented stable domain code; assigning the global template rows directly; shared mutable tenant templates; lazy copy on first login; seeder overwrite of customized tenant roles |
| RES-007-019 | Tenant role/user Actions use audit event types `tenant.role.created`, `tenant.role.updated`, `tenant.role.deleted`, `tenant.user.roles-updated`, `tenant.user.created`, `tenant.user.updated` and `tenant.user.deactivated`; role operations require exact `platform.roles.manage`, user/assignment operations require exact `platform.users.manage`, and tenant/domain rejections use `DomainException`, missing authority uses `AuthorizationException`, while invalid role/user input uses Laravel `ValidationException` field errors | Stable event identities and native exception categories make the Action contracts observable without a new exception hierarchy. | RES-007-020 | `AssignTenantRoles` atomically synchronizes the target user's complete tenant-role set; effective permissions are the additive union across that resulting set. Every role/user Action validates the persisted actor/context/target tenant identity before ID use, rejects global/foreign roles and non-catalogue abilities, restores the prior Spatie team on success or failure, and permits an otherwise-authorized Administrator to operate in an inactive selected tenant. Deactivation returns the sorted unique integer IDs supplied by owning feature queries, preserves the password hash and historical references, and never discovers or rewrites those assignments itself | One explicit synchronization contract matches the role-management form and avoids ambiguous append/remove behavior. | RES-007-021 | T007-006 creates the foundational `TenantPolicy` needed by the React/TailAdmin tenant pages, mapping global tenant view/create/update/deactivate/reactivate methods to the exact protected abilities and denying deletion; T007-020 later extends that same Policy only for branding authorization. Separating component creation from the already-owned shell hook avoids duplicate indicators and overlapping writes to global shell files. | authorization-disabled page; inline role-name checks; TenantPolicy delayed until branding; T007-006 write to unrelated shell paths; duplicate context component |
| RES-007-022 | One code-owned `PermissionCatalogue` is the canonical allowlist for protected and tenant abilities; both seeding and tenant-role Actions consume it. Tenant-user creation and complete-set role synchronization require at least one persisted same-tenant role. Role deletion fails with `TENANT_ROLE_IN_USE` when deleting its pivots would leave any tenant user with zero roles, but may proceed when every affected user retains another same-tenant role | A database permission row is mutable state and cannot prove membership in the approved catalogue. Sharing one application allowlist prevents seeder/Action drift and rejects persisted rogue abilities. Constitution C-07 and AC-007-02 explicitly require one or more roles throughout user lifecycle; guarding only create/assignment would let role deletion violate the same invariant. | treating every `permissions` row as approved; duplicated Action-local ability lists; deriving the catalogue from mutable role templates; zero-role tenant users; forbidding all deletion of assigned roles regardless of retained alternatives |
| RES-007-023 | Tenant migrations use sequence `000007–000009`, immediately after the six platform migrations and before Feature 002+ tenant-owned tables | Laravel orders migrations lexically. The former `060001–060003` names made a clean install execute master-data migrations before `tenants`, producing MySQL error 1824. Renaming only the tenancy foundation preserves schema and establishes the dependency for every later feature without renumbering all downstream migrations. | relying on incremental database history; renumbering every Feature 002–006 migration; disabling tenant FKs; creating a duplicate placeholder tenant table |
| RES-007-024 | Role/User Policies receive `TenantContext` by constructor injection and pass it explicitly into `AuthorizesTenantOwnership`; Resource/Page/Table code delegates every mutation to the seven domain Actions, role duplication is the same create-from-permission-set operation for any tenant role name, T007-010 registers both model-policy mappings in `AuthServiceProvider`, introduces one shared tenant-resource route-middleware concern used by Role/User, and removes the now-obsolete `trait.unused` PHPStan suppression from the consumed ownership concern | Filament 5.7 applies `Resource::$routeMiddleware` only to that Resource's route group. This is the narrow boundary for the required context/team/active/presentation stack: applying `ResolveTenantContext` panel-wide would deny the approved global Administrator dashboard and tenant administration when no tenant is selected. The panel separately adds these classes to Livewire's persistent middleware allowlist, which replays only middleware gathered from the original Resource route. Executable UI tests must cover the route stack, Gate mappings and Action invariants, including last-role deletion; arbitrary custom-role duplication prevents template-name behavior from becoming a domain branch. The suppression is valid only while no concrete Policy consumes the trait and would become an unmatched static-analysis ignore in this task. | panel-wide required-tenant middleware; non-persistent Livewire tenant middleware; duplicated Resource-local middleware arrays; unregistered model Policies; service-locator context in Policy methods; direct Eloquent/query-builder/pivot writes in UI; unused Action imports; permanent or unmatched static-analysis suppression; duplication special-cased for Editor/Viewer names |

## Executable gates

- teams enabled before package migration;
- team context and permission cache reset across HTTP, Livewire, console and tests;
- protected role/abilities unavailable in tenant RoleResource;
- direct-object isolation matrix across all feature resources;
- no unscoped model lookup in tenant controllers/resources/queries.
- quota lowering preserves payloads and only blocks new payload-producing Feature 003 operations;
- cross-tenant or missing-ability operational-setting changes fail safely and never mutate prior evidence.
